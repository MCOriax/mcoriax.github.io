Add-on plugin · MCIdentitySkill

Skills live on the item.

MCIdentitySkill is a standalone add-on that adds skill items to MCIdentity: items that cast a MythicMobs skill, and that only one profession may hold and use. It ships as its own jar, on its own version line, and installs alongside the core plugin.

SpigotMC PaperMC Folia Own database Requires MCIdentity + MythicMobs

What changed: abilities are no longer stored in the database

The skill system used to live inside the core plugin, with an abilities table in its database. It has been split into this add-on — and the storage did not come with it. Skill data now lives in the Minecraft item's Persistent Data Container (PDC).

Previously

Abilities in the database

  • An identity_abilities registry and an identity_equipped_abilities slot table, both removed in MCIdentity 3.0.0.
  • An ability item pointed at a row; the row was the truth.
  • Every ability read meant a lookup keyed by identity UUID.
  • Duplicating or destroying an item could disagree with the stored rows.
Now

Skills on the item (PDC)

  • A skill's definition lives on the item, not in a table — no registry row can contradict what a player is holding.
  • The item is the record. Trade it, drop it, or chest it and its data goes with it.
  • Reads are in-memory: the data is already in the item you are holding.
  • Nothing can be orphaned, and no lookup can disagree with what the player holds.
  • A database records two narrower things: which type exists on the server, and which item an identity has equipped in which slot.
💡

The core MCIdentity storage is unchanged for everything else — identities, professions, stats, and sessions are still stored in your chosen backend. Only skills moved onto the item.

⚠️

One consequence is worth stating plainly: there is no way to list which skills a player owns, and no command that could answer it. A player owns exactly the skill items in their inventory, and the only way to see them is to look at the items.

What a skill item stores

An item is a skill item exactly when its persistent data container says so — there is no registry to add it to. Every key is namespaced to the add-on, so it reads as mcidentityskill:<key> and can never be confused with another plugin's data or a vanilla tag.

📜 Any ItemStack → ItemMeta → PersistentDataContainer
  • skill_code required The MythicMobs skill ID cast when the item is used.
  • profession required The MCIdentity profession allowed to hold and cast the item.
  • display_name Human facing name shown in messages; falls back to the skill code.
  • skill_skin Model ID used for the item's visual; falls back to default.
  • cooldown_seconds Light re-use guard; absent or 0 leaves cooldown entirely to MythicMobs.

profession is stored lower-cased and trimmed, so an item created for Miner still matches a player playing miner. Text values are capped at 128 characters and the cooldown is clamped between 0 and 86400 seconds.

Malformed items

An item carrying some of these keys but missing skill_code or profession is malformed, and malformed items are always denied — never repaired, and never treated as usable by everyone. A missing profession meaning "anyone may use this" would invert the restriction the add-on exists to enforce.

An item carrying none of these keys is an ordinary item. The add-on has no opinion about it and never blocks it.

Profession restriction

A player may equip or use a skill item only while the profession of their currently active MCIdentity identity matches the profession stored on the item.

Matching is case-insensitive and ignores surrounding whitespace, because profession codes are typed by hand in both places. It is otherwise exact: there is no wildcard, no any, no prefix match, and no list of alternates. A skill item belongs to exactly one profession.

When the check runs

ActionTrigger
EquipMoving or dragging the item into a slot, or selecting the hotbar slot it already sits in.
UseRight-clicking with the item in the main hand.
PlaceAlways refused — a skill item is equipment, never a block.

The hotbar-selection case matters because an item can reach a player's hand without ever passing through the add-on — dropped by a mob, moved by a hopper, or simply still held after an identity swap.

Denials name the profession

So a player can tell an item they will never be able to use from one they only need to swap identity for:

[Skill] This skill belongs to the miner profession, but you are playing as archer.

Skill items are never placeable

A skill item is built on a player head, which vanilla treats as a placeable block. Placing one would strip the item into a block state and leave a head anyone could break and pick up, so every attempt to place a skill item is cancelled — regardless of profession, and even for a malformed item. Skill items are equipment: they are held and right-clicked, never set down.

🔒

The restriction fails closed and cannot be switched off. Anything that stops the add-on proving a player is allowed — unreadable item data, no active identity, or an unreachable core plugin — denies the action. There is no config setting that makes skill items work regardless of profession.

MythicMobs owns the behaviour

MythicMobs is a hard dependency. The skill_code stored on an item is a MythicMobs skill ID, and casting an item means asking MythicMobs to run that skill with the player as caster. Damage, targeting, particles, and effect timing are all authored in your MythicMobs configuration — if a change is about how a skill behaves, it belongs there and not in this add-on.

Order of operations

  1. Read the item from the player's hand — one persistent data container read per action.
  2. Check the profession. A denial stops here; MythicMobs is never consulted for a player in the wrong profession.
  3. Check any local cooldown declared by cooldown_seconds.
  4. Fire a cancellable event so other plugins can add restrictions of their own.
  5. Hand the skill to MythicMobs — and only now does anything actually happen.

Failure behaviour

SituationBehaviour
MythicMobs or MCIdentity missing at startupThe add-on logs a severe message and disables itself. Loading with unrestricted skills, or skills that silently do nothing, would be worse than not loading.
Unknown skill ID at cast timeLogged as a warning; the player is told the skill could not be cast. Nothing is thrown onto the game thread.
Skill ID unknown when the item is created/skill give warns immediately, but still creates the item — the skill may live in a MythicMobs pack that loads later.

Creating a skill item

/skill give Steve quarry_sense miner 45

Gives Steve an item that casts the MythicMobs skill quarry_sense, usable only while playing a miner identity, with a 45 second local re-use guard. Pass no cooldown (or 0) to leave cooldown entirely to MythicMobs.

Reading a skill item back

A skill's definition lives on the item, so reading the item is how you see it — and /skill info is that read, made visible:

[Skill] Skill item stored on this player_head:
  Skill code: quarry_sense
  Profession: miner
  Cooldown: 45s
  Usable by you: no (profession_mismatch)

Storage

Two tables, both mirroring MCIdentityRune. A skill's own definition is not in either of them — that still lives on the item.

  • SQLite — default, zero configuration
  • MySQL / MariaDB
  • PostgreSQL
  • MongoDB
  • Central REST server
TableContents
identity_skillsThe registry of skill types: system code, display name, and an optional Base64 item template.
identity_equipped_skillsWhich item an identity has equipped in which slot, keyed by identity UUID and stored as Base64.

The two are independent. A type existing does not equip it, and equipping does not require a registered type — a slot stores the item outright rather than pointing at a registry row, so the two can never contradict each other.

🔒

An equipped skill is permanent. A player may fill an empty slot and may never empty a filled one. The menu cancels every click, and the equip rules refuse to write to an occupied slot, so no command or API path can take a skill off either. Only an administrator can clear a slot, to correct a bad row.

For developers

The add-on publishes its own library modules under the io.github.mcoriax group: mcidentity-skill-api, mcidentity-skill-common, and mcidentity-skill-bukkit. Declare them compileOnly and add MCIdentitySkill to your plugin.yml: 

depend:
  - MCIdentitySkill

Two cancellable events are fired, both after the profession check has already passed — a listener never has to repeat it:

EventFired when
MCIdentitySkillEquipEventA player is about to equip an allowed skill item.
MCIdentitySkillUseEventA player is about to cast an allowed skill item, before MythicMobs is consulted.

Cancelling either one adds a restriction of your own; set a cancel reason and the player is told it. An access check reports why it denied — the profession the item requires and the one the player has — rather than a bare boolean, so you can write your own message.
