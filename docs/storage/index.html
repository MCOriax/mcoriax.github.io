Data Storage

The plugin supports multiple storage backends, selected with database.type in config.yml: SQLite (the default), MySQL, PostgreSQL, MongoDB, and the MCIdentity central server.

Standalone servers can run entirely on the zero-configuration SQLite file, while networks can share one MySQL, PostgreSQL, or MongoDB deployment — or point every node at the central REST server.

Choosing a backend

SQLite sqlite

Local file in the plugin data folder. Best for single servers; works out of the box with no setup.

MySQL mysql

MySQL or MariaDB server. Best for networks that already run a MySQL-compatible database.

PostgreSQL postgresql

PostgreSQL server. Best for networks that prefer PostgreSQL.

MongoDB mongodb

MongoDB deployment. Best for document-oriented storage or existing MongoDB infrastructure.

Central server central

MCIdentity central REST server. Best for whole networks sharing one authenticated API with token roles.

Each backend has its own connection section in config.yml:

database:
  type: sqlite
  sqlite:
    file: "mcidentity.db"
  mysql:
    host: "localhost"
    port: 3306
    database: "mcidentity"
    username: "root"
    password: "password"
  postgresql:
    host: "localhost"
    port: 5432
    database: "mcidentity"
    username: "postgres"
    password: "password"
  mongodb:
    uri: "mongodb://localhost:27017"
    database: "mcidentity"

The central type reads the existing central_server section (url, token, timeout_seconds).

How it works

  • All backends implement the same IMCIdentityDB contract, so gameplay code never knows which storage is active.
  • The SQLite, MySQL, and PostgreSQL backends share their query logic and differ only in schema DDL and upsert dialect. MongoDB stores each identity as one document with embedded properties and stats.
  • The central-server backend implements the same contract by sending asynchronous JSON requests over a single pooled HTTP client, carrying the bearer token configured in config.yml (central_server.token).
  • Every operation runs asynchronously on a dedicated worker pool, so the game thread is never blocked.
  • Reads that fail resolve to safe fallbacks (empty results or zero) so the game server keeps running; failures are logged.
  • Stat identifiers are validated against a fixed allow-list before they are used, on the plugin and (for the central server) on the API as well.

Drivers

The SQLite and MySQL JDBC drivers ship with SpigotMC, PaperMC, and Folia. The PostgreSQL driver and the MongoDB client are packaged inside the plugin JAR, so no backend requires extra downloads.

Schema

The relational backends create their tables automatically on first start:

identity_professions identity_keys identity_properties identity_stats identity_sessions identity_logs player_base_slots

The SQLite schema matches the central server's, so a database file can be moved between a game server and a central server deployment.

identity_properties

One row per identity, holding everything about it that is not a stat:

ColumnTypeContents
identity_uuidVARCHAR(36)Primary key — the identity this row describes.
aliasVARCHAR(32)The optional name the player gives this identity with /identity alias. Unique across every identity; empty until one is claimed, and never changed afterwards. Once claimed, it replaces the player's Minecraft name in chat and in the tab list while the identity is equipped. Always empty on the base player identity.

expINTExperience toward the next level.
stat_pointsINTUnspent points available to /identity stats add.

updated_atTIMESTAMPWhen the row last changed.

The alias column

An alias may contain alphanumeric characters only (a-z, A-Z, 0-9) and at most 32 of them. It is unique across every identity the backend holds, and that uniqueness ignores case — once someone holds Alex, nobody else can take alex or ALEX. The value is stored exactly as it was typed, so Alex is displayed as Alex.

Each backend enforces that rule in its own way:

BackendHow uniqueness is enforced
SQLiteA unique index over LOWER(alias).
PostgreSQLA unique index over LOWER(alias).
MySQL / MariaDBA UNIQUE constraint on a column declared with the case-insensitive utf8mb4_general_ci collation.
MongoDBA sparse unique index over a folded mirror field, stored beside the original properties.alias.
Central serverThe server owns the check and answers 409 Conflict when the alias is already taken.

The uniqueness check and the write happen together, so two players can never end up holding the same alias.

/identity alias claims a name once and never renames it afterwards, and it refuses the base player identity outright. In practice a row's alias therefore goes from empty to set exactly once, and the base identity's stays empty. The developer API is unaffected: setIdentityAlias still renames or releases, so an integrating plugin or an administrative tool can correct a name — the rule lives in the command, not in the column.

A stored alias is also the name the server shows: while the identity holding it is equipped, it replaces the player's Minecraft name in chat and in the tab list. That display is served from the session already held in memory, so naming a player costs no extra read against the backend.

ℹ️

Upgrading from 4.0.x: identity_properties gains the alias column automatically on the first start after upgrading. Nothing is dropped and no data is touched — every existing identity simply starts with no alias. On MySQL and MariaDB the column is placed directly after identity_uuid; SQLite and PostgreSQL can only append it, so on an upgraded database it sits last. Both positions behave identically.

⚠️

Upgrading from 3.x: runes and cosmetics moved into the standalone MCIdentityRune and MCIdentityCosmetic add-ons, which create and own their own tables. The first start after upgrading drops identity_runes, identity_equipped_runes, and identity_equipped_cosmetics — and, on MongoDB, the identity_runes collection and the per-identity equipped_runes and cosmetics fields. Those rows are not recoverable, and the add-ons start with empty tables rather than migrating them, so back the database up first if you want to keep them.

Upgrading from 2.x: the ability system moved into the standalone MCIdentitySkill add-on, where a skill's data lives on the item rather than in a table. The first start after upgrading drops identity_abilities and identity_equipped_abilities — and, on MongoDB, the identity_abilities collection and the per-identity equipped_abilities field. Those rows are not recoverable, so back the database up first if you want to keep them.
