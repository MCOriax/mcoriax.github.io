Change Log — MCIdentityRune 0.1.0

Permalink for MCIdentityRune version 0.1.0.

0.1.0 2026-08-03 · A rune assignment is permanent

A rune has always been described as a permanent slot assignment on an identity. It now behaves like one: /rune set fills an empty slot and refuses to write over a filled one, and an identity holds a given rune in one slot or none.

Changed An assignment is permanent

  • Equipping into a slot that already holds a rune is refused. It previously replaced whatever was there.
  • /rune clear <slot> is the only way a slot is ever emptied, and stays an operator's command. It exists to correct a bad row, not to swap runes around.
  • Moving a rune is therefore deliberate: clear the slot, then set it.

Added A rune is held once

  • Equipping a rune the identity already holds in another slot is refused.
  • Codes are compared trimmed and lower-cased, so Ember and ember are one rune. Rows written before codes were normalised are compared the same way.

Changed A refusal says which rule stopped it

  • /rune set and /rune clear now report the specific outcome — an occupied slot, a rune already held, no active identity, the base profession, or a listener's cancel — instead of one flat "that rune change was refused".
  • The change event now fires after the rules have passed rather than before the write, so a listener is no longer told about a write that was refused.

Note For server owners and integrators

  • Nothing is rewritten. An identity already holding the same rune in two slots keeps both, and every existing assignment stays where it is. The rules apply to new writes only.
  • A workflow changes. Setting straight over an old rune no longer works; run /rune clear <slot> first.
  • No storage change. Rune types and slot assignments are untouched.
  • The developer library moves to version 0.1.0, and changing a slot now reports why it was refused rather than a plain yes or no.
  • While the database is unreachable the reads that back these rules return nothing, so the checks cannot see the filled slots. The rules hold in every normal case but are not absolute during an outage.
