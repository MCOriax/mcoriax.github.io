Add-on plugin · MCIdentityRune

Runes belong to the identity, not the player.

MCIdentityRune is a standalone add-on that gives every MCIdentity identity its own set of rune slots. It ships as its own jar, keeps its own database, and installs alongside the core plugin. Open it with /rune.

SpigotMC PaperMC Folia Own database Requires MCIdentity 4.0.0+

What changed: runes left the core plugin

The rune system used to live inside MCIdentity, sharing its tables and its GUI. MCIdentity 4.0.0 removed it, and this add-on picked it up — along with the storage, which it now owns outright.

Previously

Runes inside MCIdentity

  • An identity_runes registry and an identity_equipped_runes slot table, both living in the core plugin's schema.
  • Slot 6 of the main identity menu opened a rune GUI the core plugin drew.
  • /identity rune get was a core admin sub-command.
  • Every rune change meant a release of the whole identity plugin.
Now

Runes in MCIdentityRune

  • The add-on creates and owns both tables, in its own database — with no foreign key onto anything the core plugin owns.
  • Its own /rune command and its own menu, on its own version line.
  • It reads one thing from the core: which identity you are currently wearing.
  • Either plugin can be upgraded without waiting for the other.
⚠️

Upgrading the core to 4.0.0 drops identity_runes and identity_equipped_runes from its database, and this add-on starts with empty tables rather than migrating them. Existing rune assignments are not recoverable — back the database up first if you want to keep them.

Every row is keyed by identity

A rune is equipped by an identity, never by a player. Two identities owned by the same person wear entirely separate runes, and swapping identity swaps the whole rune set with it.

This is the invariant the whole add-on is built around: every read and every write is keyed by the identity UUID resolved from the core plugin's session cache, never by the player UUID. A player with no active identity has nothing to read and nothing to write to.

SituationResult
Wearing a profession identityallowed — reads and writes that identity's slots
Wearing the base player professiondenied — the base profession may not use runes
No active identitydenied — there is nothing to key the row by
Core plugin unreachabledenied — the add-on fails closed rather than guessing
Identity swapped mid-interactionThe write still lands on the identity that was resolved when the action started, never on the new one.
🔒

A failed read returns an empty result, never another identity's runes. There is no fallback that could show one identity the equipment of another.

The rune menu

/rune with no arguments opens a six-row menu for the identity you are wearing. Equipped slots show the rune's display name; empty slots show a placeholder. The layout is fixed, because the slot numbers are stored in the database and existing rows reference them.

Ten slots per identity. The last one is the ultimate slot, set apart in the layout but stored exactly like the others. Clicking a slot equips or clears it; every other click in the menu is cancelled so nothing can be dragged out of it.

Registering and equipping a rune

/rune register ember Ember Sigil
/rune set 1 ember
/rune clear 1

Rune codes are stored lower-cased and trimmed, so Ember and ember are the same rune. A slot number outside 1–10 is rejected before anything reaches the database.

Storage

The add-on keeps its own storage and picks its backend the same way the core plugin does, with database.type in its own config.yml.

  • SQLite — default, zero configuration
  • MySQL / MariaDB
  • PostgreSQL
  • MongoDB
  • Central REST server
TableContents
identity_runesThe registry of rune types: system code and display name.
identity_equipped_runesWhich rune sits in which slot, keyed by identity UUID.

Neither table carries a foreign key onto a core plugin table. That is deliberate: it is what lets the two plugins be upgraded, and even backed by different databases, independently. Schema creation is idempotent and runs on every start; every query binds its parameters, and the only identifiers ever interpolated come from a frozen allow-list.

💡

Every database call runs off the game thread on the add-on's own worker pool, so a slow or unreachable database never stalls the server — see the core plugin's Data Storage page for the same model applied to identities.

Installing

RequirementWhy
Java 25 or newerMatches the core plugin's toolchain.
SpigotMC, PaperMC, or FoliaOne universal jar; the server type is detected at enable time.
MCIdentity 4.0.0 or newerHard dependency. It owns the identity a rune is attached to, and 4.0.0 is the release where it stopped shipping a competing rune system of its own.
A databaseOptional in practice — SQLite is the default and needs no setup.
  1. Drop MCIdentityRune-<version>.jar into plugins/, alongside MCIdentity.
  2. Start the server once. It writes plugins/MCIdentityRune/config.yml and then disables itself, because enable defaults to false.
  3. Set enable: true, and pick a database.type if you do not want SQLite.
  4. Restart the server.
# Master switch. The plugin generates no data files and registers nothing
# until this is turned on.
enable: false

# Storage backend for runes.
database:
  type: sqlite
  sqlite:
    file: "mcidentityrune.db"

On an older core the add-on logs a warning at startup rather than refusing to enable — but that core still ships its own rune GUI, so players would see two competing rune systems. Upgrade the core plugin.

For developers

The add-on publishes its own library modules under the io.github.mcoriax group: mcidentity-rune-api, mcidentity-rune-common, and mcidentity-rune-bukkit. Declare them compileOnly and add MCIdentityRune to your plugin.yml: 

depend:
  - MCIdentityRune
EventFired when
MCIdentityRuneSetEventA rune is about to be equipped into, or cleared from, a slot. Cancellable — cancelling refuses the change before it reaches the database.

The event carries the player, the identity UUID the change targets, the slot number, and the rune code (null when the slot is being cleared). Bind your own data to the identity UUID, never to the player UUID — that is the key the add-on itself uses.
