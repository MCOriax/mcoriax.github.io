Add-on plugin · MCIdentityCosmetic

Every identity wears its own look.

MCIdentityCosmetic is a standalone add-on that gives every MCIdentity identity its own skin and aura. It ships as its own jar, keeps its own database, and installs alongside the core plugin. Open it with /cosmetic.

SpigotMC PaperMC Folia Own database Requires MCIdentity 4.0.0+

What changed: cosmetics left the core plugin

Skins and auras used to be columns on the core plugin's own tables, drawn by a menu the core plugin owned. MCIdentity 4.0.0 removed them, and this add-on picked them up — storage included.

Previously

Cosmetics inside MCIdentity

  • An identity_equipped_cosmetics table in the core plugin's schema, plus getSkin() and getAura() on its identity properties.
  • Slot 8 of the main identity menu opened a cosmetic GUI the core plugin drew.
  • Loading a session fetched cosmetics whether anything used them or not.
  • Every cosmetic change meant a release of the whole identity plugin.
Now

Cosmetics in MCIdentityCosmetic

  • The add-on creates and owns its table, in its own database — with no foreign key onto anything the core plugin owns.
  • Its own /cosmetic command and its own menu, on its own version line.
  • It reads one thing from the core: which identity you are currently wearing.
  • Either plugin can be upgraded without waiting for the other.
⚠️

Upgrading the core to 4.0.0 drops identity_equipped_cosmetics from its database, and this add-on starts with an empty table rather than migrating it. Existing skins and auras are not recoverable — back the database up first if you want to keep them.

Two independent fields

An identity wears a skin and an aura, and the two are entirely independent. Changing one never clears the other.

FieldValueNotes
skinA Base64 texture blobDeliberately not length-capped — a full profile-property texture is a large value, and truncating it would produce a broken skin rather than a rejected one.
auraA system codeTrimmed and capped at 255 characters, the same shape every other code in the ecosystem uses.

Both are optional. A blank value and an absent value mean the same thing — nothing worn — so clearing a field and never setting it are indistinguishable, by design. An identity that has never touched the add-on reads back as wearing neither, not as missing.

💡

Each field is written by its own statement, so a skin save can never blank an aura and an aura save can never blank a skin — even when two changes race. The column a write targets comes from a frozen two-entry allow-list; anything else is rejected before a statement is built.

Every row is keyed by identity

A cosmetic is worn by an identity, never by a player. Two identities owned by the same person can look completely different, and swapping identity swaps the look with it.

Every read and every write is keyed by the identity UUID resolved from the core plugin's session cache, never by the player UUID. A player with no active identity has nothing to read and nothing to write to.

SituationResult
Wearing a profession identityallowed
Wearing the base player professionallowed — the base profession may wear cosmetics like any other
No active identitydenied — there is nothing to key the row by
Core plugin unreachabledenied — the add-on fails closed rather than guessing
Identity swapped mid-interactionThe write still lands on the identity that was resolved when the action started, never on the new one.
🔒

Unlike runes, cosmetics are not restricted by profession. The base player identity is a real identity that may wear a skin and an aura like any other — the restriction that applies to runes was never a cosmetic rule.

The cosmetic menu

/cosmetic with no arguments opens a one-row menu for the identity you are wearing, showing what it currently wears in each of the two slots.

Setting and clearing

/cosmetic aura ember
/cosmetic skin eyJ0ZXh0dXJlcyI6eyJTS0lOIjp7InVybCI6...
/cosmetic aura clear

Clearing one field leaves the other exactly as it was. /cosmetic info reads the stored row back, so it is the way to confirm what an identity actually wears.

Storage

The add-on keeps its own storage and picks its backend the same way the core plugin does, with database.type in its own config.yml.

  • SQLite — default, zero configuration
  • MySQL / MariaDB
  • PostgreSQL
  • MongoDB
  • Central REST server
TableContents
identity_equipped_cosmeticsOne row per identity: its skin and its aura, either of which may be absent.

The table carries no foreign key onto a core plugin table. That is deliberate: it is what lets the two plugins be upgraded, and even backed by different databases, independently. Schema creation is idempotent and runs on every start; every query binds its parameters, and the only identifiers ever interpolated come from a frozen allow-list.

Installing

RequirementWhy
Java 25 or newerMatches the core plugin's toolchain.
SpigotMC, PaperMC, or FoliaOne universal jar; the server type is detected at enable time.
MCIdentity 4.0.0 or newerHard dependency. It owns the identity a cosmetic is attached to, and 4.0.0 is the release where it stopped shipping a competing cosmetic system of its own.
A databaseOptional in practice — SQLite is the default and needs no setup.
  1. Drop MCIdentityCosmetic-<version>.jar into plugins/, alongside MCIdentity.
  2. Start the server once. It writes plugins/MCIdentityCosmetic/config.yml and then disables itself, because enable defaults to false.
  3. Set enable: true, and pick a database.type if you do not want SQLite.
  4. Restart the server.
# Master switch. The plugin generates no data files and registers nothing
# until this is turned on.
enable: false

# Storage backend for cosmetics.
database:
  type: sqlite
  sqlite:
    file: "mcidentitycosmetic.db"

For developers

The add-on publishes its own library modules under the io.github.mcoriax group: mcidentity-cosmetic-api, mcidentity-cosmetic-common, and mcidentity-cosmetic-bukkit. Declare them compileOnly and add MCIdentityCosmetic to your plugin.yml: 

depend:
  - MCIdentityCosmetic
EventFired when
MCIdentityCosmeticSetEventA skin or an aura is about to be set or cleared. Cancellable — cancelling refuses the change before it reaches the database.

The event carries the player, the identity UUID the change targets, which of the two fields is changing, and the new value (null when the field is being cleared). Bind your own data to the identity UUID, never to the player UUID — that is the key the add-on itself uses.
